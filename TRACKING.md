## How To Decide

| If tracker says      | User does                                                                            |
| -------------------- | ------------------------------------------------------------------------------------ |
| blank or In Progress | Follow the exact `Next Action`; if it starts with `User input:`, provide that input. |
| Implemented          | Run `/ref-verify "Page Name :: Section Name"`.                                       |
| Verified             | Stop; that target is done.                                                           |
| Blocked              | Provide the exact missing input named in `Next Action` or `Notes`.                   |
| Reference changed    | Run `/ref-sync`; otherwise do not use sync as part of the normal loop.               |

## Tracker Rules

| Rule           | Detail                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Scope          | Reference inventory is based on `reference/`; progress also reflects React code, mock API coverage, comparison, and checks. |
| Purpose        | Track what pages/features exist, what big sections each page has, what APIs each section uses, and what to do next.         |
| Progress       | Leave blank until a section/page is intentionally compared, started, implemented, or verified.                              |
| API source     | Use `reference/concept_endpoint_overlay.js` as the primary API map.                                                         |
| Section source | Use visible page structure from reference HTML plus endpoint overlay guide layouts.                                         |
| Contract       | Response shapes must come from an accepted contract source; do not infer them from reference UI.                            |

## Progress Values

| Value       | Meaning                                                                                       |
| ----------- | --------------------------------------------------------------------------------------------- |
| blank       | Not assessed yet.                                                                             |
| Planned     | Chosen for upcoming work.                                                                     |
| In Progress | Currently being rewritten.                                                                    |
| Implemented | React version exists and focused checks passed.                                               |
| Verified    | React version was compared against the reference and accepted; `pnpm check` passed.           |
| Blocked     | Waiting on API contract, response contract, sample data, route choice, behavior, or decision. |

## Build Readiness Values

| Value               | Meaning                                                                                               |
| ------------------- | ----------------------------------------------------------------------------------------------------- |
| Ready               | Required endpoint and accepted response shape are available.                                          |
| Static-only         | `API Used` is `None`, and all content and behavior are visible in the reference.                      |
| Already implemented | React code exists for the target; use `/ref-verify` unless a small build fix is still needed.         |
| Blocked             | Required endpoint, response shape, sample payload, route choice, UI behavior, or decision is missing. |

## Accepted Contract Evidence

Accepted response contract sources are a documented backend/API response contract, a user-provided sample payload, or a fixture explicitly approved by the user as the contract for that exact endpoint. Record accepted sources in the relevant row notes or API Contract Matrix notes before treating a section as ready. Mock fixtures can support implementation, but fixture-backed data is not verified contract data unless explicitly accepted.

Blocked notes should name the exact missing endpoint, response shape, sample payload, route choice, UI behavior, or decision plus the user input needed to unblock the row.

Overlay-only rows are inventory/API maps, not visual build targets, unless the user provides a visual reference or explicitly approves visual-only implementation for the exact target. Visual-only mock approval can support `Implemented`; it does not allow `Verified` for dynamic/API behavior until the response contract is accepted.
